The definitive test is whether the package product has `SBQQ__ProductOption__c` children. Run these in the Developer Console query editor.

**Is anything in your org configured as a bundle:**

```sql
SELECT SBQQ__ConfiguredSKU__r.ProductCode, SBQQ__ConfiguredSKU__r.Name, COUNT(Id)
FROM SBQQ__ProductOption__c
GROUP BY SBQQ__ConfiguredSKU__r.ProductCode, SBQQ__ConfiguredSKU__r.Name
ORDER BY COUNT(Id) DESC
```

If your packages show up in that list, they're CPQ bundles and the class handles them today. If the list is empty or contains only unrelated products, they're not.

**Check a specific package directly:**

```sql
SELECT Id, SBQQ__OptionalSKU__r.ProductCode, SBQQ__OptionalSKU__r.Name, SBQQ__Required__c
FROM SBQQ__ProductOption__c
WHERE SBQQ__ConfiguredSKU__r.ProductCode = 'YOUR-PACKAGE-CODE'
```

**Stronger evidence — look at a quote someone already built correctly.** If quotes exist that were assembled through the CPQ line editor, they're ground truth for the structure you're trying to reproduce:

```sql
SELECT SBQQ__Product__r.ProductCode, SBQQ__RequiredBy__c, SBQQ__RequiredBy__r.SBQQ__Product__r.ProductCode,
       SBQQ__ProductOption__c, SBQQ__Bundle__c
FROM SBQQ__QuoteLine__c
WHERE SBQQ__Quote__c = 'PASTE_A_QUOTE_ID'
ORDER BY SBQQ__Number__c
```

`SBQQ__RequiredBy__c` populated on the product lines means the package is a bundle parent. All nulls means the products are flat lines and the package is a grouping that exists somewhere other than the product data.

**One more signal, less reliable:**

```sql
SELECT Name, ProductCode, SBQQ__ConfigurationType__c, SBQQ__OptionSelectionMethod__c
FROM Product2
WHERE ProductCode = 'YOUR-PACKAGE-CODE'
```

`SBQQ__ConfigurationType__c` indicates CPQ expects the product to be configurable. I'd treat it as corroborating rather than conclusive — a product can carry that setting with no options actually defined, and the `ProductOption` query is what settles it either way.

If all of those come back empty, the package concept lives in your CMT rather than in CPQ's product data — which is the second case I described, and the one where this class needs no changes but something upstream has to expand packages into product codes first.

Structurally yes — it parses cleanly and maps to the `QuoteInput`/`LineInput` shape exactly. The bundle-with-option plus standalone-line combination is the mixed case the class is built for.

Whether it *runs* depends on four things in your org. Note that `Site_Count__c`, `Device_Type__c`, and all three product codes were placeholders I invented in the original example — none of them are verified against your data.

**Fields on `SBQQ__QuoteLine__c`.** `Site_Count__c` and `Device_Type__c` must exist and be writable. If not: `Unknown field on SBQQ__QuoteLine__c: Site_Count__c`. If they exist but are formula or read-only: `Field is not writable for the running user`.

**Fields on `SBQQ__Quote__c`.** `SBQQ__StartDate__c` and `SBQQ__SubscriptionTerm__c` are real CPQ fields, but confirm they're updateable in your version rather than formula-driven.

**Product codes.** All three must exist on `Product2`. Missing ones come back as `Unresolvable product codes: NET-BUNDLE, ROUTER-01`.

**The option relationship.** `ROUTER-01` must be a configured option of `NET-BUNDLE`. If not: `ROUTER-01 is not a configured option of NET-BUNDLE.`

Verify all of it before running anything:

```sql
SELECT QualifiedApiName, DataType, IsCalculated
FROM FieldDefinition
WHERE EntityDefinition.QualifiedApiName = 'SBQQ__QuoteLine__c'
  AND QualifiedApiName IN ('Site_Count__c','Device_Type__c')
```

```sql
SELECT ProductCode, Name, IsActive FROM Product2
WHERE ProductCode IN ('NET-BUNDLE','ROUTER-01','SVC-INSTALL')
```

```sql
SELECT SBQQ__OptionalSKU__r.ProductCode FROM SBQQ__ProductOption__c
WHERE SBQQ__ConfiguredSKU__r.ProductCode = 'NET-BUNDLE'
```

Two behaviours worth expecting rather than debugging:

`Device_Type__c` is set to `"Edge"`. If that's a picklist, deserialization accepts any string — the validity check happens at insert, so a bad value surfaces as a DML error naming the picklist, not as a payload error.

The parent `NET-BUNDLE` line gets `SBQQ__Quantity__c = 1` and `ROUTER-01` gets 12, exactly as written. CPQ's own configurator would normally derive option quantity from the bundle, but nothing here does that — your payload is authoritative. If you expected 12 routers to follow from something about the bundle, it won't.
