Probably not for the first release. I oversold it earlier.

The test is narrow: **can one generic generator produce every table you need, differing only by config?** If yes, metadata means new tables ship without Apex. If each table needs its own classification or filtering logic, the metadata is indirection on top of code you're writing anyway — you get a config record *and* a new Apex branch.

For three hardcoded tables (Product Family Summary, Product Detail, Transaction Summary), a switch on `Table_Code__c` with the definitions as Apex constants is less machinery and easier to debug. You still get the value of `Table_Code__c` as a stable identifier — that part stands on its own and doesn't depend on where definitions live.

Two things that push toward metadata later:

- **Count.** At roughly five-plus definitions the switch statement becomes the thing people are afraid to touch.
- **Who authors them.** If an admin or BA is expected to add "Industry Summary" without a developer, config has to live outside Apex. If it's always a developer, Apex constants are honest about that.

One limitation worth knowing before you plan on it: Custom Metadata handles flat key-value well but has no native ordered list. Grouping dimensions in order (`Industry → Product Family → Product`) need either a delimited text field you parse, or a child CMDT with a sequence number. Applicable measures have the same problem. Both work; neither is clean, and the parsing code is code you'd otherwise not write.

My recommendation: build the generator so table definitions are a data structure it consumes — an Apex class with `groupingDimensions`, `filter`, `measures`, `label`. Populate that structure from constants now. If the count grows or authorship shifts to admins, swap the source to CMDT without touching the generation logic. The abstraction that matters is the generator reading a definition object, not where the definition is stored.
