## Verdict

**Use `SBQQ__Quote__c` as the DocuSign CLM source/root record, but do not flatten this generated document data into fields directly on the Quote.** Your current relationship is the right shape:

```text
SBQQ__Quote__c
└── Quote_Document_Table__c
    └── Quote_Document_Row__c
```

DocuSign’s current Salesforce documentation supports custom-object mappings, nested tables, and fields from up to **two levels of related lists**. Your Quote → Table → Row hierarchy fits that documented limit exactly. ([Docusign Support][1])

The schema itself has the right document-generation characteristics: stable `Table_Code__c`, explicit ordering, signed measures, stored display labels, product snapshots, hidden-but-counted rows, precomputed totals, and a clear separation between Quote Lines as the source of truth and generated rows as document data. 

## What should be stored directly on the Quote

Only store **generation orchestration and readiness**, not the seven measures or row content.

I would add these fields to `SBQQ__Quote__c`:

* `Document_Data_Status__c` — Not Generated, Generating, Ready, Stale, Failed
* `Document_Data_Generated_On__c`
* `Document_Data_Generation_Version__c`
* `Document_Data_Error__c` — optional, short admin-facing failure summary
* `Current_Document_Generation_Key__c` — only if you retain multiple generations

The important field is `Document_Data_Status__c`. DocuSign is launched from the Quote, so it needs one authoritative answer to:

> “Are all document tables for this Quote complete, mutually consistent, and safe to consume?”

Per-table `Status__c` cannot give the Quote-level launch action that answer without additional querying.

I would **not** copy these onto Quote:

* `Amount_Net_New__c`
* `Amount_Cancellation__c`
* the other document measures
* grouping values
* row counts per table
* display labels
* table-specific totals

Those are document projections. Putting them on the Quote would create a second commercial model beside CPQ and would become ambiguous when the same Quote has several tables with different `Amount_Basis__c` values.

A scalar belongs on Quote only when it is a genuine Quote business fact used outside document generation—not merely because DocuSign needs to print it.

## The main issue in the current design

I would not finalize generation rule 2 without an additional guarantee:

> “Regenerate by deleting existing rows and re-inserting.”

There are two risks.

### 1. Quote-level consistency

With multiple tables, `Status__c = Complete` on one table does not prove that every other table belongs to the same generation. CLM could theoretically receive:

* Transaction Summary from generation 12
* Product Family Summary from generation 11
* Industry Summary from generation 12

This is safe only when **all tables and rows are replaced in one all-or-nothing Salesforce transaction**, followed by the Quote being marked Ready.

### 2. Historical reproducibility

The row snapshot fields preserve product names and labels only until the next regeneration. Once the rows are deleted, Salesforce no longer retains the source snapshot that produced an earlier signed document.

That may be acceptable when the signed PDF in CLM is the only required historical artifact. But the schema should not claim full reproducibility after regeneration unless old generations are retained. 

## Recommended publication model

Because your hierarchy already consumes the two documented related-list levels, I would **not immediately insert a third `Quote_Document_Generation__c` object between Quote and Table**. That may complicate direct Gen-template traversal.

Instead, bring `Is_Current__c` back from the deferred list when generation cannot be guaranteed in one transaction.

Add to `Quote_Document_Table__c`:

```text
Generation_Key__c
Is_Current__c
```

Change the table key from:

```text
QuoteId:TableCode
```

to:

```text
QuoteId:GenerationKey:TableCode
```

Then publish this way:

1. Mark the Quote `Generating` or `Stale`.
2. Create an entirely new set of table and row records with `Is_Current__c = false`.
3. Validate every table and all cross-table reconciliations.
4. In one final transaction:

   * mark the previous tables non-current;
   * mark the new tables current and Complete;
   * update the Quote’s current generation key;
   * mark the Quote Ready.
5. Permit CLM generation only when the Quote is Ready.

This avoids exposing partially replaced data. It also lets you retain the precise source data used for signed documents. Old generations can later be deleted under a defined retention policy.

When historical retention is explicitly unnecessary and every table fits into one transaction, the existing delete-and-reinsert approach is reasonable—but the Quote-level status gate is still needed.

## The CLM consumption contract

The DocuSign template should have a very simple responsibility.

### Root

```text
Source object: SBQQ__Quote__c
```

### Table selection

For `Quote_Document_Table__c`:

```text
Status__c = 'Complete'
Is_Current__c = true          // when versioning is implemented
ORDER BY Display_Order__c
```

### Row selection

For `Quote_Document_Row__c`:

```text
Is_Displayed__c = true
ORDER BY Display_Order__c
```

DocuSign Gen currently documents SOQL-based filtering and sorting for child data in table-row fields, so `Display_Order__c` should be explicitly applied rather than relying on Salesforce relationship order. ([Docusign Support][2])

CLM should:

* print the values;
* conditionally render based on `Row_Type__c`;
* indent based on `Group_Level__c`;
* select the appropriate section using `Table_Code__c`.

CLM should **not**:

* recalculate subtotals;
* infer transaction classifications;
* determine whether bundle children count;
* sum visible rows;
* calculate grand totals.

Your schema correctly keeps that logic in Apex.

## A few specific schema decisions

### Keep the table-level measure fields

Duplicating the seven measures on `Quote_Document_Table__c` and on the Grand Total row is justified. It makes a total directly mergeable outside a repeating row and gives you an easy reconciliation assertion.

That duplication is much better than copying the values to Quote.

### Keep `Is_Displayed__c`

For DocuSign, this becomes a real integration filter rather than merely presentation metadata. Hidden-but-counted bundle children remain available for arithmetic integrity but are excluded from the generated document.

### Keep the rows flat for rendering

`Parent_Row__c` is useful for validation and hierarchy integrity, but CLM should not recursively walk `ChildRows`. The combination of:

```text
Display_Order__c
Row_Type__c
Group_Level__c
```

gives CLM a deterministic flat render stream. That is considerably safer than asking the template to reconstruct a tree.

### Treat `Row_Count__c` as diagnostic

It is useful for Apex assertions, tests, logging, and integration diagnostics. I would not describe it as something the CLM Word template itself will necessarily compare automatically.

### Do not rely only on Quote `LastModifiedDate`

`Generated_On__c > Quote.LastModifiedDate` is not a sufficient freshness contract because the generated data also depends on Quote Lines and potentially related records.

Use either:

* explicit stale marking whenever relevant Quote or Quote Line data changes; or
* a source-generation fingerprint/version captured during calculation.

### Freeze API names after template rollout

Your stable API naming is important. DocuSign documents that changing or deleting Salesforce fields used by a Gen template can cause document generation failures. Treat these fields as an integration API once templates are deployed. ([Docusign Support][3])

### Decide what Quote deletion means

Master-detail is correct for disposable generated data. But it also means deleting a Quote deletes the tables and rows. Either accept that intentionally, prevent deletion after document execution, or use a different retention arrangement when the Salesforce snapshot must survive independently.

## Final recommendation

I would approve the overall object model with this position:

> **Quote is the owner and CLM launch record. Quote Document Tables and Rows are the generated document snapshot. Quote stores only the readiness and current-generation state.**

The one material change is to establish a **Quote-level readiness boundary**. Then either guarantee whole-Quote generation in one transaction or implement staged generations with `Generation_Key__c` and `Is_Current__c`.

I would not move the table measures or row content onto the Quote merely to make DocuSign consumption easier.
